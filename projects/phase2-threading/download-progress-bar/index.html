Download Progress Bar

Several download workers run at once and all want to move the same bar. The naive version has each worker do total += chunk on a shared counter — a read-modify-write that loses bytes when two chunks land at the same moment, so the bar silently stalls below 100%. This one removes the race instead of locking it: every worker reports only its own cumulative position — an absolute, monotonic number — and one aggregator owns the sum. Absolute updates are idempotent and order-independent, so replaying, dropping or reordering them leaves the total exactly right. First of two tasks in karan/Projects' Threading category. The same engine drives real concurrent HTTP range-downloads under Node (see the README); this page simulates the workers so you can watch — and sabotage — the coordination.

Chaos log

With chaos on, each report is randomly dropped, duplicated or delayed/reordered before reaching the aggregator — exactly what unpredictable concurrent delivery does. The overall bar still lands on 100% because positions are absolute: a dropped update is undone by the next one, and a stale/duplicate update is a no-op.

The aggregator, the EWMA rate, the ETA and the bar renderer all live in progress-core.js with no DOM and no sockets; this page and progress-node.js just feed it updates. Part of a daily automated Claude Code routine — see the repository README.md and PROGRESS.md.
