**The task (karan/Projects):** *"Online White Board — Create an application
which allows you to draw pictures, write notes and use various colors to flesh
out ideas for projects. Optional: Add feature to invite friends to collaborate
on a white board online."*

A whiteboard looks like a weekend project: a `<canvas>`, a `mousedown`, draw a
line to wherever the mouse goes. That version works for about ten seconds, and
then every hard thing about a whiteboard shows up at once. This build is built
around the three that actually matter.

## 1 · A whiteboard is a *document*, not a bitmap

The naive save is one line:

```js
localStorage.board = canvas.toDataURL();   // ← throws the whole drawing away
```

That saves **pixels**. The moment you do, you've lost everything that makes a
whiteboard a whiteboard: you can't undo a stroke, you can't erase one shape
without smearing a hole in the others, you can't move or recolor anything, and
you can't export it as anything but a fixed-resolution PNG that turns to mush
when you zoom.

So the board here is never stored as pixels. It's a **list of vector
elements** — each stroke keeps its own points, color, width and opacity; each
shape and text note keeps its geometry. Pixels are only ever a *rendering* of
that list, regenerated on demand. Everything good follows from that one choice:

- **Undo / redo** is manipulation of the element list, not the canvas.
- **The eraser** does real geometry — point-to-segment distance against each
  stroke (`hitTest` in `whiteboard-core.js`) — and removes *elements*, so it
  never leaves a white scar.
- **Save** (`.wbd`) writes the element list as JSON. Reload it and every stroke
  is still editable.
- **Export** goes two ways: **PNG** (rasterize the list at 2× with a white
  background) and **SVG** — real, infinitely-scalable vector output.

## 2 · Freehand strokes need smoothing, not line segments

Join raw pointer samples with `lineTo` and you get a visibly polygonal stroke —
every tiny jog of the mouse becomes a corner. The fix is a specific, classic
construction: draw a **quadratic Bézier through the midpoint of each pair of
samples**, using the sample itself as the control point. The curve passes
smoothly through every midpoint and bends toward every sample, turning a noisy
polyline into a continuous, natural line.

```
samples:   •      •      •      •          naive (lineTo):   ∕\∕\   (corners)
            \    / \    /                   smoothed (Q):    ∿∿∿∿   (one curve)
```

The important detail: **the canvas drawing and the SVG export are generated by
the same algorithm** (`drawSmoothPath` and `pathD` in `whiteboard-core.js`), so
what you export is curve-for-curve identical to what you drew. The naive version
is kept too (`pathDNaive`) — the tests assert the smoothed path is all `Q`
commands and the naive one is all `L`, so the two can never quietly drift apart.

## 3 · "Invite friends to collaborate" is a *convergence* problem

The optional feature is the deep one. Two people drawing on one board, edits
crossing in flight — the question that decides whether a collaborative editor
works is: **when the dust settles, does everyone see the same thing?** Naively
broadcasting "draw this now" does *not* guarantee that. Messages arrive in
different orders on different screens, get duplicated by a flaky network, race
against each other — and the boards drift apart.

The engine solves it the way real collaborative editors do, with a
**conflict-free, append-only operation log**:

- Every editor is a **replica** with a [**Lamport clock**](https://en.wikipedia.org/wiki/Lamport_timestamp).
- Every edit — add a stroke, delete one, clear the board — is an **immutable
  operation** stamped `(lamport, siteId)`. Nothing is ever mutated in place.
- The visible board is a **pure function of the *set* of operations**, with the
  elements ordered by `(lamport, siteId)`. Deletes are tombstones; a clear hides
  everything created at or before it.

Because the board is a deterministic function of an *unordered set* with a
*total order* applied, **every replica that has seen the same operations
computes the identical board** — no matter what order they arrived in, or how
many times. That's the convergence property, and it's exactly what `tests.js`
checks: it generates a set of edits, delivers them to two replicas in *shuffled,
duplicated* order, and asserts the two serialized documents are byte-identical.

```
node tests.js
  ...
  ✓ replicas A and B converge to an identical document
  ✓ B's delete of A's stroke is respected on both
  ✓ a fresh replica loading a snapshot converges too
  ✓ re-delivering an op is a no-op
  ✓ concurrent clears converge
```

### The transport is deliberately swappable

The engine never mentions the network — it just emits and ingests operations.
The browser app wires those operations to a **`BroadcastChannel`**, so **opening
the room link in a second tab gives you real, live, multi-user collaboration
with no server at all**: strokes, shapes and notes appear on both boards as they
happen, remote cursors and all. Point the same engine at a WebSocket instead and
it collaborates across the internet, unchanged. (BroadcastChannel links tabs in
one browser — it's the honest, serverless demonstration of the model the engine
is built for.)

## The whiteboard itself

Open `index.html`. You get:

- **Tools:** pen, highlighter (translucent), straight line, rectangle, ellipse,
  text notes, and an eraser. Shapes snap to square/circle with **Shift**.
- **Various colors** (the task's words) — a palette plus a full custom picker —
  and an adjustable stroke size; optional fill for shapes.
- **Undo / redo** (`Ctrl+Z` / `Ctrl+Y`), **Clear**, and single-key tool
  shortcuts (`P H L R O T E`).
- **Save** / **Load** vector documents, **export PNG** (2×) and **export SVG**.
- **Collaborate** — start a room, copy the link, open it elsewhere, draw together.
- A **crisp canvas on hi-DPI screens** — the canvas is sized by
  `devicePixelRatio` so strokes aren't blurry on retina displays, a thing the
  one-line version always gets wrong.

| `whiteboard-core.js` | the whole engine — vector element model, midpoint-Bézier stroke smoothing (canvas **and** SVG from one algorithm), the Lamport-clock replica / op-log that guarantees convergence, hit-testing, rendering, SVG export, and save/load serialization. No DOM, no canvas, no network. |
| `index.html` + `script.js` + `style.css` | the browser whiteboard: a hi-DPI canvas, pointer input for mouse/touch/pen, live preview, undo/redo as operations, the toolbar, and `BroadcastChannel` collaboration with live remote cursors. |
| `whiteboard-node.js` | a headless CLI over the same engine — build a sample board and **save** it (`.wbd`) and export **SVG** with no browser, replay a saved document to SVG, or run the two-replica convergence demo. |

## Run it

**The whiteboard** — open `index.html`, start drawing. Click **Collaborate**,
copy the link, open it in another tab, and draw on both.

**The CLI** (Node, no dependencies):

```bash
# build a sample board; save it as a vector doc AND export SVG, no browser:
node whiteboard-node.js --demo --out ./board      # writes board.wbd + board.svg

# replay a saved document to SVG (this is "save them" end to end):
node whiteboard-node.js --to-svg board.wbd

# watch two replicas converge after shuffled delivery:
node whiteboard-node.js --converge
#  identical documents after shuffled delivery: YES ✓
```

**The tests:**

```bash
node tests.js
#  ✓ 45/45 checks passing
```

## What this demonstrates about the web

The drawing part of a whiteboard is the easy, boring part. What separates a toy
from a real one is everything underneath: modeling the board as editable vector
data instead of pixels (so save, undo, erase and scalable export are even
*possible*), smoothing freehand input with a real curve construction shared
between screen and export, and — for the "invite friends" feature — making
independent replicas provably **converge** on the same board no matter how the
network reorders or duplicates their edits. Get the data model and the op-log
right and "draw, write notes, use various colors, collaborate" all fall out of
it. Reach for `canvas.toDataURL()` and `base + href`-style string hacking, and
you have a board you can't undo, can't scale, and can't actually share.
