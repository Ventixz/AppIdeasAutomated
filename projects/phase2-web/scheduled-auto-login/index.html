Scheduled Auto Login & Action

Source 2 (karan/Projects) · Web · the scheduling and resilient-session engine behind "log in on a schedule and do something" — run entirely offline against a mock site. Built by an automated Claude Code routine.

Scope & responsibility. There is no real third party here. The hard, interesting parts of this task are when to run, how to survive a site saying "no," and how to keep secrets out of your logs — all pure logic, shown below. For a real service, drive its official API within its terms of service, and keep credentials in the environment, never in code.

1 · When does it run, and what happens when the site says no?

"Every day at 09:00" is not "now + 24h" — it is the next wall-clock occurrence, recomputed each time. And a login or action can fail, or a session can silently expire. Set it up and run a simulated window: watch the fire times land on schedule and the engine back off, give up, or re-authenticate. The clock and the randomness are seeded, so it is repeatable.

2 · Exponential backoff with jitter

Retrying a failed login immediately, in a tight loop, is how you get blocked and how a crowd of clients syncs into a spike. The fix is to wait longer after each failure (exponential), capped, and to jitter the wait so clients don't retry in lockstep. Drag the controls and watch the retry delays.

3 · Keeping secrets out of your logs

A scheduler that prints its config to debug will happily print the password too — and now it's in a log file forever. redactSecrets masks any field whose name looks secret, so logging the whole config is safe by default. Edit the config and watch what a log would actually show.
